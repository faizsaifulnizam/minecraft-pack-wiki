# Exploration reference B

FULL SPOILERS — encounter rewards and progression-item roles follow.

## Baseline
Private candidate-r2; unapplied and not canonically adopted. Twilight Forest 4.8.3345 retained text, not runtime-confirmed drops. Read [Exploration reference A](https://faizsaifulnizam.github.io/minecraft-pack-wiki/full/exploration-reference-a/) for the actual advancement requirements; [Preparation](https://faizsaifulnizam.github.io/minecraft-pack-wiki/guides/exploration-preparation/) for retreat and death recovery.

## Evidence status
These are **loot-table declarations**. A table's name is not proof that a particular death, chest or completed fight calls it. Selected custom number providers and multiplayer functions were not implemented/traced here; do not turn their parameters into guaranteed totals per player. Effective overrides, looting, difficulty and runtime award routing remain unknown. Inventory criteria in reference A are not loot rewards generated by the advancement; the selected advancement objects do not contain `rewards` fields.

## Prerequisites
Spare inventory room, a safe retreat and an opportunity to compare the actual item with its identifier. Do not activate a scepter, lamp or trap just to inspect it: their effect controls and costs were not traced. This page gives item-handling checkpoints, not combat tactics or a boss-spawn route.

## Steps
1. Use the corresponding row after an encounter or find. Compare the actual inventory, not only the toast or display icon. Numbers below are **literal base table parameters before modifier functions**, not measured final drops.

Lamp inventory + merge progression is the declared `progress_troll` condition. [R11, A] |

2. Keep progression-relevant finds until the corresponding inventory or consumption checkpoint is actually confirmed. Deposit unrelated rare gear before the next branch; consumable food has a different checkpoint from persistent trophies. Do not discard the only relevant item merely because an adjacent node is visible.
3. Compare the branch endpoints in reference A before moving upward. The merge needs all three endpoints; a complete reward set is neither specified nor a substitute. A trophy in storage is not proof of each player's current advancement state.
4. If a listed item does not appear, retreat and retain what you did obtain. These tables alone cannot distinguish custom roll behaviour, a different dispatch route, override, item loss, sharing, or a failed encounter completion. Repeating the fight blindly is not a verified repair.
5. If death interrupts collection, re-equip before attempting recovery. Do not assume drops never despawn, a trophy is safely recoverable, or a custom award can be recreated by taking damage. No recovery guarantee or boss-reset method was traced.

## Expected result
A reward-oriented checklist aligned with the condition route, without invented award triggers, fixed party shares, guaranteed chests or all-items drop promises. Actual loot dispatch and combat remain pending; side treasures and every optional collection task are not exhaustively covered.

Useful tip: compare **item ID, criterion and table** as three separate facts. Benefit: exposes traps such as fiery tears in prose but not the progression predicate, or a giant pickaxe icon with a beans predicate. Trade-off: more reading than following icons alone; still no runtime proof.

## Common failures
- **A base count is the final total.** Modifiers and custom number providers are present. This page deliberately reports their declared input parameters rather than inventing implementation results.
- **An advancement generates its displayed reward.** An icon is not a reward function. These selected progression definitions have no `rewards` object.
- **The special trophy table must run when I kill one phantom.** Its caller was not traced; table existence is insufficient.
- **The lamp table guarantees a generated vault contains it.** Placement, chest binding and runtime generation were not established.
