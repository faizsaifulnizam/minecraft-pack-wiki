# Accessory slot reference and conditional UI check

## Baseline

Development documentation snapshot **dev-0.5-20261015-r2**; not release validation. Static documentation only; effective datapacks, settings and gameplay have not been verified.

## Evidence status

Curios' shipped README describes tag-based item eligibility, merged slot identifiers and the equipment GUI. This supports a bounded reference and conditional attempted UI check, not a proven equip/removal procedure, stacking bonuses, duplicate-item acceptance or a fixed slot count. Exact placement/removal controls and item predicates remain unresolved. The README says applicable Curses work on equipped items; it does not establish a specific curse rule or guaranteed removal. Artifacts and Relics both supply feet-slot definitions; their individual declared sizes must not be added together as an effective capacity claim.

## Prerequisites

An already-obtained, nonvaluable accessory with no known applicable binding or removal restriction, one empty main-inventory cell, and a positively identified matching functional slot. Unknown removal restrictions or unidentified slots are a stop condition, not permission to experiment with valuables. Acquisition is separate. Read its Slot tooltip; do not choose a slot from the item's name.

## Steps

1. In Controls, find Curios → Open/Close Curios Inventory. Use its current binding; the shipped README says the default is G, not that this pack still uses G.
2. Read the matching slot label and item tooltip. “Toggle Visibility” and “Toggle Cosmetics” are shipped control labels only, not verified behavior or a way to identify functional versus cosmetic cells. Do not infer semantics from labels or slot appearance; do not place valuables in unidentified slots. If the functional slot or operation is unclear, stop here.
3. Only if the prerequisite and identified UI permit it, attempt placement of one nonvaluable accessory using the UI's identified operation. Exact clicks/drag controls are unresolved here; no gesture is prescribed. If placement is denied, stop; do not force placement or drop the item.
4. If placement succeeds, inspect the occupied slot. This observation does not prove ability execution or save persistence.
5. If an identified removal operation is available, attempt return to the reserved main-inventory cell. If removal is denied or its control is unclear, stop and ask the host; do not force removal or drop the item. Do not assume this check is reversible.

## Expected result

The conditional check may show placement and, if permitted, removal; either may remain unresolved or be denied. No successful check has been observed here, and removal is not guaranteed. No claim that merely holding it activates its equipped effects. Continue with [Relic research](https://faizsaifulnizam.github.io/minecraft-pack-wiki/guides/relic-research/) or [personal loot handling](https://faizsaifulnizam.github.io/minecraft-pack-wiki/guides/personal-loot/). Optional [Full-spoiler content omitted] contains named items and recipes.

## Common failures

- No slot: Curios does not provide a universal default set; integrations supply slots. Do not edit settings to create one for this guide.
- Wrong slot, unidentified cell or inactive tooltip: stop and inspect eligibility without further placement. If removal is denied, ask the host; do not force or drop. Cosmetic visibility is not an effect test.
- Inventory full: clear a safe cell first; do not drop the accessory as a workaround.
- Death, disconnect or missing item after reload: recovery and persistence are not established here. Do not assume soulbinding, gravestone support or keep-inventory. Ask the host before risking valuable equipment.

Tip: read slot labels and removal restrictions at a safe base before an expedition. A conditional check with a nonvaluable item may expose a conflict, but is not guaranteed reversible and does not establish loadout synergy.

# Personal loot and the shared container

## Baseline

Development documentation snapshot **dev-0.5-20261015-r2**; not release validation. Static documentation only; effective datapacks, settings and gameplay have not been verified.

## Evidence status

This exact Lootr release describes unique loot for each player opening a loot container. Its shipped warnings explicitly say breaking the block or destroying the entity prevents other players obtaining loot. Personal contents therefore do not make the physical container disposable. Conversion eligibility, refresh configuration and claim permissions are not established by that description.

## Prerequisites

A container positively identified as Lootr, room for the items you intend to take, and host permission to interact. Ordinary base storage is not assumed personal. Do not probe by breaking a container.

## Steps

1. Agree that each player opens the intact Lootr container themselves. Do not nominate a first opener to distribute everyone's supposed contents.
2. Open normally and take the items you want into your inventory. Leave the physical container in place for other players.
3. A second player opens it independently. Their own contents are the intended checkpoint; different rolls need not be identical. This is a proposed group check, not a reported test.
4. Close it and return supplies to agreed shared storage yourself. Personal loot does not mean items subsequently placed in ordinary storage remain private.
5. Before moving on, read any displayed refresh or decay message. These messages describe timed states; their presence in translations does not mean either feature is enabled for every chest.

## Expected result

Players can distinguish their loot from the shared access point and preserve access for the group. Continue with [equipment slot reference](https://faizsaifulnizam.github.io/minecraft-pack-wiki/guides/equipment-slots/).

## Common failures

- Cannot break: respect the refusal. Shipped messages mention sneak-breaking overrides in some contexts; they are destructive warnings, not a recovery instruction.
- Empty after returning: do not promise a refill or run refresh/clear commands. Timers and conversion can be configured; ask the host with the container's displayed identity, without publishing coordinates.
- Container decayed or destroyed: no player restoration procedure is documented in the retained evidence. Stop interacting and request host assessment; commands may change everybody's state.
- Claim denies access: Lootr ships an FTB Chunks whitelist tag reference, but that does not prove effective permission policy. Team/claim permissions require a separate host check.

Tip: open as a group before leaving rather than removing the chest. This preserves access but still cannot guarantee later availability if decay is enabled.

# Research an already-owned relic

## Baseline

Development documentation snapshot **dev-0.5-20261015-r2**; not release validation. Static documentation only; effective datapacks, settings and gameplay have not been verified.

## Evidence status

The exact release's UI text supplies the research gesture, constellation task and wrong-container recovery. This is a research task, not a proven acquisition route or an executable numerical leveling build. Costs are dynamic UI substitutions, not fixed numbers recoverable from the translations.

## Prerequisites

An already-owned Relics item in the player's main inventory. Locate Controls → Research relic under the cursor. Have room to keep the item in inventory. Use [equipment slot reference](https://faizsaifulnizam.github.io/minecraft-pack-wiki/guides/equipment-slots/) separately.

## Steps

1. Hover the relic in the main inventory and hold the currently bound research control shown by the tooltip. Do not assume a default keyboard letter.
2. In the research interface, choose an ability available at the item's current level. A low-level message means it is not ready; do not spend resources attempting to bypass it.
3. For an unresearched available ability, connect hidden stars so the constellation matches its background image. The shipped tip says correct alignment automatically researches the ability.
4. Check that the unresearched prompt is gone. Read the ability and Experience Sources tabs before using it. An experience source can itself require an associated ability to be unlocked and researched.
5. For later planning, distinguish relic experience from vanilla player experience and leveling points. The UI says relic level-ups increase the upgrade-point pool; ability upgrades also list player-XP costs. Read the current cost before any purchase. This guide does not direct spending or prescribe an untraced upgrade click.

## Expected result

An available ability is researched through the documented puzzle. This does not establish its equip requirement, combat effect or save persistence. Optional [Full-spoiler content omitted] gives a separate exact cooking upgrade.

## Common failures

- Wrong-container message: move the relic to the player's main inventory and retry; this is the release's explicit recovery.
- Hint offers a price: hints consume displayed player experience. Solve manually to avoid that expense; Shift offers automatic research, not a free shortcut.
- Quality mistaken for ability level: UI text calls quality a visual summary of random characteristics. A higher quality display is not itself more levels.
- Reroll/reset: do not use them as free undo. Both display player-XP costs, and rerolling can replace perfect values; Shift can automate costly repeated operations.

Tip: inspect Experience Sources before training. It identifies relevant use instead of wasting unrelated XP; exact quantities remain item- and state-dependent.
